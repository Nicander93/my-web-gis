# GeoLibre 对标与下一阶段建议

日期：2026-10-03。以本仓库当前代码与 GeoLibre 官方文档为依据，属于产品规划和局部代码检查，不是完整安全、性能或全仓审计。

参考：[空间处理](https://geolibre.app/user-guide/processing/)、[属性表](https://geolibre.app/user-guide/attribute-table/)。GeoLibre 文档列出空间/属性连接、几何有效性与拓扑检查、重投影、栅格分析和多格式转换；这些是对标线索，未在此逐项运行其应用。

## 产品优先级

| 顺序 | 补齐能力 | 本项目状态与价值 | 验收任务 |
| --- | --- | --- | --- |
| 1 | 按区域统计、空间连接、属性连接 | 有基础字段统计、筛选和按位置提取，缺少把多个图层组合成业务结果的工具 | 行政区汇总站点数量、数值合计和均值；表格按编码连接区域；明确边界、重复匹配、空值和无匹配规则 |
| 2 | 几何检查与修复、线裁剪 | 已有面算法前置校验，尚无可定位的独立问题报告；裁剪仅支持面 | 导入含自交/孔洞错误的数据，定位问题、选择修复并保留原数据；道路裁剪到行政区，检查多段结果与属性 |
| 3 | 字段计算、面积/长度、CRS 与格式互通 | 已有 CSV/DXF 的坐标转换基础，尚无完整处理/导出 CRS 流程；不能把经纬度平面结果当作米制面积/距离 | 声明坐标系与单位，按表达式生成字段；选取一种实际需要的交换格式（例如 GeoPackage）完成往返 |
| 4 | 凸包、简化、沿线采样、批量运行 | 常用工具可继续接现有 Worker；增加数量前先完善查找和任务反馈 | 一组固定真实数据完成处理链，验证几何误差、耗时、取消、保存重开和导出 |
| 按用例立项 | 栅格、路网、点云、大型计算引擎 | 当前以二维矢量与独立三维场景编辑为主，这些任务涉及新的数据模型/运行环境 | 先选明确场景和数据规模，再决定成熟库、WASM 或本地服务；不一次复制全部工具目录 |

二维分析与三维场景编辑分别规划。三维的分组/锁定、多选变换与对齐，不与二维空间连接合并成一次泛化架构改造。

## 代码已具备的基础

- Core、Runtime、应用 Command、UI 有清晰边界；Turf/JSTS 算法复用，UI 不直接做布尔几何。
- 处理输入范围一致，Worker 隔离计算，取消可终止 Worker；项目切换防止迟到结果写入其他项目。
- 输出为独立数据集，保存处理来源与参数；自动测试覆盖属性隔离、边界、孔洞、多部件、保存重开及取消。
- 捕捉偏好独立于项目状态，设置切换不替换 Draw/Modify；参照层与可编辑层分离。

## 尚未完善的工程项

1. **结果图层撤销（2026-10-04 已补）**：处理与要素复制结果使用 `AddLocalLayerCommand`，同时恢复 Dataset、Layer、顺序、要素缓存和选择。自动测试与浏览器区域统计验证已覆盖撤销和重做。
2. **规模与性能**：`gis-core/processing.ts` 面相交逐个配对，最坏为 A×B；`OlMapRuntime.syncLayers` 每次对既有源 clear/addFeatures。应先建立代表性数据基准，再添加包围盒候选索引与按层/要素增量同步。
3. **工具元数据**：当前工具定义、表单分支和标签散布多个模块。下一批加入连接/统计时整理轻量工具目录，统一输入几何约束、参数、单位、来源版本及结果类型；暂不引入插件框架。
4. **任务可解释性**：当前每次一个 Worker，可取消但没有计算进度或数据规模提示；来源记录不含输入快照/选择 ID，不能保证复跑同一结果。区分结果说明与可重放历史，先明确需求再增加存储。
5. **坐标与几何契约**：处理使用 WGS84，部分算法限制跨日期变更线或极区；缺少完整几何诊断/修复与投影工作流。第三维 Z 的保留/丢弃策略也需要逐工具明确。
6. **真实流程验收**：单元测试和生产构建不能替代 WebView 中导入、Worker、取消、捕捉、撤销、文件保存、重启与导出验证。保留第一阶段 P21 的未完成状态，不因本次测试通过而改成完成。

## 建议下一次交付

## 核心扩展包也是产品交付

用户于 2026-10-03 明确：项目既要是好用的桌面工具，也要提供业务开发中常用、可复用的工具库。后续新增功能同时按两种交付验收：

- 算法、输入输出契约和可复用规则放入合适的核心扩展包，不依赖 React、Zustand、桌面会话或弹窗；地图引擎交互留在对应 Runtime。应用 Command 负责项目、选择、Worker 和结果落库。
- 新能力先提供小而明确的类型化公共 API、独立调用示例和契约测试，明确坐标系、单位、边界、空值、错误及属性策略。优先薄适配成熟库，不把其内部实现类型直接泄漏为公共契约。
- 每次交付检查相关包及依赖的独立构建、声明文件和公开入口，再检查 Desktop 集成构建/测试。用构建后的包入口验证外部调用，避免只在源码 alias 下可用。
- 保持按真实能力划分的包边界；不把所有算法持续塞进 gis-core，也不为每个小工具建立新包。空间处理形成独立稳定模块后再评估提取为处理扩展包；领域类型和项目协议继续放在 Core。
- 面向未来发布记录依赖、许可证、API 兼容性与最小示例；正式 npm 发布单独安排，不因本条要求立即发布或引入插件框架。

下一批区域统计的验收包含：业务代码直接调用核心 API 获得统计结果，以及桌面用户完成同一处理流程。两者共享算法实现。

### 下一条完整业务流程

完成“行政区汇总站点”一条端到端流程：区域与站点输入 → 关系选择 → count/sum/mean 字段 → 保留零匹配区域 → 独立结果 → 撤销 → 保存重开 → 导出。明确共边界点与重叠行政区是否多次计数，并将规则展示在参数旁。几何运算沿用成熟库，聚合与字段命名保持薄适配；同时补结果图层撤销和候选范围索引。

本次提交前验证：GIS Core 67、OL Runtime 17、Desktop 111 项测试通过；另有 5 项已有环境依赖测试跳过。Desktop 与依赖生产构建通过，保留大包和混合导入警告。此记录不声明所有上述工程项已经解决。

2026-10-04 进展：第一优先级的区域统计、属性连接和空间连接已实现；算法交付为独立 `spatial-analysis` 扩展包，构建产物可由 Node 与 TypeScript 业务代码直接消费。结果撤销同步补齐。验证范围与限制见[第四批记录](phase-2-spatial-processing.md#第四批区域汇总与连接2026-10-04)。下一优先级仍为几何诊断与可定位的问题报告，不能因算法前置校验存在而视为已交付。

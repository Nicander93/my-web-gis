# 项目恢复草稿

恢复草稿保存在本机，是未保存工作的副本，与正式的 `.webgis.json` 文件分开管理。正式保存仍然是在同目录写临时文件再原子替换。草稿写入失败时，项目内容、未保存状态、撤销/重做记录和正式文件都不会改变。

## 写入时机与保留策略

- 文档有修改后，空闲 5 秒写入一次；持续编辑时每 120 秒补一份快照。这两个间隔由 `startRecoveryTracking(delayMs, intervalMs)` 的参数控制。页面转入后台时会尝试写入，但无法保证异步 IO 一定能在进程退出前完成。
- 写入的内容包括已应用的图层、几何、属性和三维场景，以及运行时的地图视图和相机。布局、选中集、表格偏好、未应用的表单预览和凭据值都不进快照。
- Windows 上存放在 Tauri 的 `app_local_data_dir()/project-recovery`，浏览器上存放在 IndexedDB 的 `desktop-webgis-recovery`。浏览器上的存储和下载证据不能代替原生验收。
- 单份草稿最大 32 MiB，最多保留 20 个项目，总量 128 MiB。超出限制时拒绝新的写入，保留原有缓存。已验证能正常使用的草稿保留 30 天，启动检查时清理过期项；损坏或版本未知的草稿会保留，直到用户明确舍弃。
- 项目 ID 以 UTF-8 十六进制的形式作为键，不能当路径使用。原生缓存接口不接受正式项目的路径，会检查目录和文件是否是符号链接，草稿只写进应用自己的缓存目录。
- 前端有一条串行队列，存储层再做条件写入和删除，两者共同保证版本正确。Windows 上用独占文件句柄协调不同的应用进程，进程退出后由系统释放锁，不会留下需要手工清理的占用。未完成的原子写入留下的临时文件，超过一天后按受限的命名规则清理。

最后一次成功写入之后的新编辑，可能还没有进入恢复缓存。界面提示写入失败时，应当保存正式项目。恢复机制不保证每次按键都已持久化，也不提供断电无损的保证。

## 启动后的处理

启动后如果发现草稿，会提示：

1. 有正式文件路径时，先做只读比较。内容完全一致的草稿按版本条件清理；内容不同，或正式文件无法读取时，保留草稿并给出提示。
2. 选择「恢复草稿」会加载完整快照，保留项目、图层和对象的 ID，并标记为未保存副本。工作文件路径会被清空；之后通过保存对话框明确选择位置，不会自动覆盖可能已被外部修改的正式文件。草稿继续保留，确认保存当前版本后才清理。
3. 「舍弃草稿」只删除所选的缓存版本，不删除正式项目。损坏或版本未知的草稿不能恢复，但可以明确舍弃。
4. 「暂不处理」保留缓存，下次启动时再次提示。已有其它会话的待处理草稿不会被自动写入覆盖；检查或舍弃时遇到版本变化，可以重新检查。

新建或打开项目时如果明确放弃文档修改，会在实际替换成功后清理该会话的草稿；取消文件选择则保留当前内容和恢复能力。一般的项目切换会保留前一个未保存项目的独立草稿。保存失败、保存期间编辑或切换项目、清理草稿期间继续编辑，这几种情况下都不能把旧的一次写入当作当前的保存确认。

## 验证方式与边界

自动化入口：

```powershell
rtk pnpm --filter @desktop-webgis/desktop build
rtk pnpm --filter @desktop-webgis/desktop test
rtk pnpm --filter @desktop-webgis/desktop test:e2e project-recovery.e2e.ts --project=laptop --project=desktop --project=wide
rtk proxy node apps/desktop/scripts/native-recovery-acceptance.mjs
cd apps/desktop/src-tauri
rtk cargo test --lib --locked
```

- `project-recovery.test.ts`：覆盖草稿格式、隔离、脱离引用、坏数据、凭据、保留期、写入失败、旧版本舍弃和会话清理。
- `recovery-tracking.test.ts`：覆盖修改合并、会话偏好隔离、项目切换、失败重试、明确放弃和取消选择。
- `project-save.test.ts`：覆盖写入及清理期间的新修改、会话切换、保存失败和清理失败。
- `project-recovery.e2e.ts`：使用真实 IndexedDB，覆盖编辑属性后关闭再重开、舍弃损坏草稿、三维分组 ID 和光照设置的恢复、完整保存和缓存清理。关闭前会逐项确认最新编辑已经进入缓存。
- Rust 测试：覆盖真实的 Windows 文件、大小与数量限制、独占句柄、损坏文件的版本保护；两个子进程分别在写入中和草稿提交后直接退出，由父进程检查旧文件完整性和缓存能否重读。两个子测试默认标记为 ignored，只由父测试在专用目录中调用，不属于未执行的验收项。

## Windows 原生验收

`native-recovery-acceptance.mjs` 会编译一个独立应用标识的版本，在 5197 端口启动自己的 Vite 服务，通过 9229 连接真实的 WebView2。启动后检查 `isTauri`、原生应用标识和应用数据目录，不能用浏览器模拟原生桥。端口被占用时不会复用其它实例；结束时只终止自己启动的进程树，并重新构建普通的 debug 配置。独立的测试缓存和 WebView 配置保留在测试命名空间中，不使用日常的应用缓存。

2026-10-14 的最终运行让两组真实的 Tauri 进程强制退出后重启，均通过：

- 二维：先保存 value=2 的正式文件，再通过属性表计算改成 42，核对 Windows 草稿文件中已是新值后强制结束应用。重启恢复后，Dataset、Layer、Feature 的内容和 ID 完全一致，旧正式文件逐字节未变；用另一个原生工作文件保存完成后，缓存清空。
- 三维：加载真实 GLB，保存基准项目，把等比缩放改为 2，检查原生缓存后强制退出。重启后重新加载模型，参数、对象 ID、节点和资源一致，原生保存和草稿清理都通过。渲染显隐对照：51,355 个特征像素降到 14,806 个背景像素，再恢复到 51,348 个，说明目标模型确实重新显示。

实际 WebView 视口为 1037×648，devicePixelRatio 约 1.39，这不能替代 Windows 125% 缩放的验收。保存时使用预先绑定的测试工作文件路径，再点击真实 UI 保存，走的是真实原生写入；系统文件选择窗口没有自动化。第一次尝试在自动定位飞行途中保存，节点相同但相机从约 2462m 移到约 183m，版本保护正确地保留了未保存状态；最终测试改为等视图稳定后再保存，没有放宽保存确认条件或像素断言。

证据包括原生恢复启动截图、恢复后的 GLB 与缩放参数、原生运行报告。报告对应的运行标识为 `com.desktop-webgis.recovery-acceptance-1791971406313`。

系统文件选择窗口、Windows 125% 缩放、完整的本地资源组合，以及 Tileset 裁剪与压平，仍需单独验收。这里的原生 GLB 像素证据不代表 M8 的 GPU 效果已经完成。
